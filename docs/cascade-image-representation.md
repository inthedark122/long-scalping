# Cascade image representation

The cascade detector is the execution layer for the live strategy. Stairs
describe the structural pattern; cascade decides whether the current movement
has enough direction, speed, continuation range, and adverse-room to trade it.
The image remains a research/debug representation of the same numeric signal.

## Source of truth

The image must be a projection of the same chronological event stream used by
the detector:

1. read one 1-minute candle with its MRC bands and volume fields;
2. update `detection::cascade::CascadeState` with the candle;
3. save the returned `CascadeSignal` beside that candle;
4. render a rolling window ending at the current candle.

The renderer must never calculate a signal from pixels. Numeric candle, MRC,
volume, and cascade data remain the source of truth; the image is a debug,
labeling, and future model-training artifact.

## Canonical frame

Use one fixed-size frame per symbol, timeframe, and observation time. A frame
contains:

- the last 128 one-minute OHLC candles;
- the nine MRC lines for each candle, including the mean line;
- volume gain and buy/sell gain bars;
- one `CascadeSignal` per candle;
- the active movement envelope and completed movement boundaries;
- a JSON manifest with the source range, normalization values, and feature
  version.

The future renderer should accept a typed frame rather than rereading a CSV.
That keeps replay, live snapshots, and generated images on the same schema.

## Visual layout

Render SVG first because it is deterministic, inspectable, and does not add a
binary image dependency to the live module. Convert the SVG to PNG only for
consumers that require raster input.

The canonical canvas is 256 by 256 pixels:

- the upper 192 pixels show candles and MRC lines;
- the lower 48 pixels show volume;
- 8 pixels remain as a border;
- the current candle is marked with a vertical guide;
- the active cascade movement is shown as a translucent directional envelope;
- completed movements are separated with thin vertical markers;
- reversal, counter-move, and stretched points use fixed symbols;
- colors, line widths, and phase symbols are versioned and must not vary by
  asset or price level.

Price is normalized per frame using the combined candle and MRC range with a
small fixed padding. Volume uses `log1p` followed by a per-frame percentile
cap so one abnormal bar cannot erase the rest of the volume shape. The raw
normalization values are stored in the manifest so the frame is reversible for
inspection.

## Labels and leakage control

The image contains only information available at its ending timestamp. Future
movement, trade result, selected pattern, and PnL belong in the sidecar
manifest as labels, never in the pixels. A frame must therefore be generated
before its outcome is resolved and labeled later during replay.

Recommended files:

```text
frames/<symbol>/1m/<timestamp>.svg
frames/<symbol>/1m/<timestamp>.json
frames/<symbol>/1m/<timestamp>.png       # optional derived artifact
```

The manifest should include `schema_version`, symbol, timeframe, start and end
timestamps, the raw price/volume normalization, cascade phase and direction,
and later outcome labels. It should also identify the exact source replay so a
frame can be regenerated byte-for-byte.

## Execution role

For a staircase candidate, the live gate uses cascade information in this
order:

1. confirm that the cascade direction matches the staircase direction;
2. require a measured positive movement speed;
3. require the cascade continuation range to reach the planned target;
4. reject a recent adverse movement larger than the planned stop;
5. reject counter-moves and reversals.

When the gate is ready, limit entries can be split into up to three marked
orders across the observed adverse range. The exit can also be split into up
to three reduce-only target orders. The aggregate budget and structural stop
remain shared, so staging does not multiply the allowed risk.

## Implementation boundary

When this is needed, add a research-only renderer next to the replay tooling,
for example `module/src/bin/research/cascade_image.rs`, or move it into a
dedicated research crate if the renderer grows. It should expose a pure
`render_svg(frame)` function and a CLI that accepts replay data and an output
directory. It must not be imported by the live engine.

The first implementation should have tests for deterministic output, fixed
canvas dimensions, bounded coordinates, and rejection of NaN or incomplete
frames. PNG conversion can then be a separate build step using a standard SVG
renderer, without changing the detector or the trading strategy.
